# 图像灰度转换 NEON 优化实验报告

## 一、实验目的

在鲲鹏 920 (ARMv8-A) 平台上，使用 NEON SIMD 指令集对 RGB→Gray 灰度转换进行优化，通过对比纯 C、NEON Intrinsics、NEON 汇编、多路循环展开等方案，探究 SIMD 并行加速的实际效果、最优展开度以及性能瓶颈所在。

---

## 二、算法原理

### 2.1 灰度转换公式

BT.601 标准定义的 RGB 转灰度公式：

$$Gray = 0.299 \cdot R + 0.587 \cdot G + 0.114 \cdot B$$

浮点运算效率低，工程中使用整数近似（系数乘以 $2^8 = 256$ 后用移位还原）：

$$Gray = (77 \cdot R + 150 \cdot G + 29 \cdot B) \gg 8$$

### 2.2 并行性分析

每个像素的三个通道（R/G/B）独立计算，像素之间无数据依赖。输入为 8bit 三通道交错排列（RGBRGBRGB...），输出为 8bit 单通道。这种"相同操作作用于大量数据"的模式天然适合 SIMD 并行处理。ARMv8 NEON 支持 128bit 向量寄存器，一次可处理 8 个 16bit 元素或 16 个 8bit 元素。

## 四、实验方案

### 4.1 五种实现

| 版本 | 描述 | 每轮处理 |
|------|------|------|
| C (baseline) | 纯 C 逐像素标量循环 | 1 像素 |
| NEON x1 | 基础 NEON，无展开 | 8 像素 |
| NEON x2 | 2 路循环展开 | 16 像素 |
| NEON x4 | 4 路循环展开 | 32 像素 |
| NEON x8 | 8 路循环展开 | 64 像素 |
| NEON x16 | 16 路循环展开 | 128 像素 |

### 4.2 关键 NEON 指令

```
vld3_u8   — 一次加载 3×8 bytes，自动分离 R/G/B 通道
vmovl_u8  — 8bit → 16bit 扩展，防止乘法溢出
vmulq_u16 — 16bit 向量乘法
vmlaq_u16 — 16bit 向量乘加（累加）
vshrn_n_u16 — 16bit → 8bit 窄化，带移位
vst1_u8   — 存储 8 个灰度结果
```

### 4.3 编译

```bash
gcc -O2 -march=armv8-a+simd -Wall -o gray_test \
    main.c gray_c.c gray_neon.c gray_neon_asm.S \
    gray_neon_x2.c gray_neon_x4.c gray_neon_x8.c gray_neon_x16.c -lm
```

## 五、实验结果

### 5.1 随机数据测试 (1920×1080 = 2,073,600 像素)

| 版本 | 耗时 (ms) | 加速比 |
|------|------|------|
| C | 4.17 | 1.00× |
| NEON(x1) | 2.68 | 1.56× |
| NEON(Asm) | 2.67 | 1.56× |
| NEON(x4) | 2.18 | 1.91× |

### 5.2 真实图片测试 (1624×1080 = 1,753,920 像素)

| 版本 | 耗时 (ms) | 加速比 |
|------|------|------|
| C | 2.93 | 1.00× |
| NEON(x1) | 1.71 | 1.71× |
| NEON(x2) | 1.50 | 1.95× |
| **NEON(x4)** | **1.36** | **2.15×** |
| NEON(x8) | 1.72 | 1.70× |
| NEON(x16) | 1.70 | 1.72× |

注：多次运行中 x8/x16 耗时在 1.62~1.72 ms 间波动，x1~x4 波动 < 0.03 ms。x8/x16 区间的较大波动间接印证了寄存器溢出导致的访存行为对内存对齐和调度顺序的敏感性。

### 5.3 正确性验证

所有 NEON 版本输出与纯 C 基准版逐像素完全一致（OK），无计算误差。

### 5.4 展开度—加速比曲线

```
加速比
  │
2.2× │             ●(x4, 2.15×)
2.0× │       ●(x2, 1.96×)
1.8× │ ●(x1, 1.71×)          ▲(x16, 1.80×)
1.7× │                        ▲(x8, 1.70×)
     │
1.0× │──(C, 1.00×)
     └──────┴──────┴──────┴──────┴──────
     x1     x2     x4     x8     x16
```

**最优展开度为 x4（32 像素/轮），加速比 2.15×。x8 出现明显性能衰退。**

## 六、结果分析

### 6.1 理论加速比与实际加速比的差距

NEON 一次处理 8 个像素（8 路 SIMD lane），理论上可达 8× 加速。实际最优仅 2.15×，差距来自以下原因。

### 6.2 访存瓶颈分析

灰度转换是典型的**访存受限（Memory-Bound）**算法：

$$运算强度 = \frac{3乘 + 2加 + 1移位}{3B读 + 1B写} = \frac{6\ \text{ops}}{4\ \text{B}} = 1.5\ \text{ops/byte}$$

鲲鹏 920 单核理论计算峰值远高于内存带宽的承载能力。计算如下：

| 指标 | 数值 |
|------|------|
| NEON x4 实际处理速度 | 1,753,920 像素 / 1.36 ms ≈ 1.29 Gpixel/s |
| 有效带宽 | 1.29 Gpixel/s × 4 B ≈ **5.16 GB/s** |

实际有效带宽远低于鲲鹏 920 单核 L2 理论带宽（~30 GB/s），瓶颈不在 L2→L1 通道本身，而在于 `vld3_u8` 的交错访存模式（stride-3 gather）无法利用连续内存传输的突发优势。

### 6.3 展开度 x8/x16 性能反降分析

核心原因：**NEON 寄存器溢出（Register Spilling）**。

AArch64 NEON 共有 32 个 128bit 向量寄存器 (v0-v31)：

| 展开度 | 最少寄存器需求 | 是否溢出 |
|------|------|------|
| x1 | 7 (3数据 + 3系数 + 1结果) | 否 |
| x4 | 19 (12数据 + 3 + 4) | 否 |
| **x8** | **35 (24数据 + 3 + 8) > 32** | **溢出** |
| x16 | 67 (48 + 3 + 16) | 严重溢出 |

编译器被迫将溢出部分临时存入栈内存（spill/fill），额外的访存操作消耗了大量时间，导致展开收益被完全抵消甚至反转。这也是 x8（1.72 ms）几乎退化到 x1（1.71 ms）水平的原因。

### 6.4 Intrinsics 与汇编性能对比

| 版本 | 耗时 | 差异 |
|------|------|------|
| NEON Intrinsics | 2.66 ms | — |
| NEON 汇编 | 2.63 ms | < 1.2% |

两者差异在测量噪声范围内。表明 GCC 对 NEON Intrinsics 的代码生成质量足够优秀，手写汇编无法获得额外收益。这一结论与 AArch64 平台的特点一致——AAPCS64 规范的寄存器分配策略和编译器优化在简单循环场景下已接近最优。

### 6.5 随机数据与真实图片的性能差异

真实图片（2.93 ms）比随机数据（4.17 ms）快约 42%——真实图像像素具有空间局部性，相邻像素颜色相似，CPU 硬件预取器效率更高，Cache 命中率更高。

### 6.6 替代 perf 分析

由于实验环境无 sudo 权限，无法使用 `perf stat` 获取硬件计数器。通过以下替代方法进行分析：

1. **展开度曲线实验** — 通过 x1→x16 的性能变化，反推出寄存器瓶颈和访存瓶颈
2. **运算强度计算** — 由 ops/byte 比值判断算法属于 memory-bound
3. **多数据集对比** — 随机数据 vs 真实图片，验证 cache 行为对性能的影响

---

## 七、结论

1. NEON SIMD 对灰度转换有明显加速效果，最优展开度 x4 下加速比达到 **2.15×**（真实图片）
2. 性能瓶颈为**访存受限**（`vld3_u8` 的 stride-3 gather 无法利用突发传输），而非计算资源不足
3. 循环展开并非越多越好：超过 x4 后因**NEON 寄存器溢出**导致性能下降，x8 退化至接近 x1 水平
4. 编译器对 NEON Intrinsics 的代码生成与手写汇编性能相当（差异 < 1.2%），工程中优先使用 Intrinsics
5. 真实图片因更好的空间局部性，性能优于随机数据 42%
